# 上帝沙盘模拟器 · God Sandbox

一个**画面粗糙、低多边形、程序化纹理平涂**风格的桌面沙盘模拟器。
你以上帝视角在沙盘上雕刻地形、放置建筑、观察简化物理。

> 纯前端静态站点：无后端、无付费 API、无联网多人。构建产物可直接部署到 GitHub Pages。
> 刻意不追求照片级写实，也不声称拟真现实 —— 目标是**可运行、可调试、可扩展**。

## M2.5 第一部分修了什么（对照本轮 3 个问题）

| # | 问题 | 做法 |
| --- | --- | --- |
| 1 | 堆叠不是重合成一个，而是叠罗汉 | **堆叠逻辑整体重写**（`building/StackingSystem.ts`）。每个物体仍是独立实体，A 放在 B 顶面时 A 的底部 Y = B 的顶部 Y；下方有多个物体时**取最高支撑面**；记录层数并在超过 20 层时提示 |
| 2 | 一个物体顶面只能放一个物体 | **支撑面共享**（`building/SupportSurface.ts`）。顶面是一块**有面积的资源**：记录总面积 / 已占用 / 剩余，每个物体占一块。放置时把顶面按 4×4 小网格（可调）划格，每个空闲格子都是候选点 —— 一张桌子上就能整齐摆一排 |
| 6 | 初始地图仍然太大 | 新手从 64×24×64 缩到 **48×16×48**（9 区块 / 2 万体素，比上一轮再少一半），标准缩到 96×24×96，大型 192×32×192。剔除距离按档位分档 6/8/12，新增质量预设与自适应降级 |

补充实现：堆叠与支撑调试面板、稳定性三色提示（绿/黄/红）、按住 Shift 的连续堆叠工具、按住 Ctrl 的对齐辅助、一键「性能优先 / 画质优先」预设。

### 关键修复：为什么之前会"重合成一个"

根因是**暂停时放置的碰撞检测完全失效**：
Rapier 的查询管线只在 `world.step()` 里更新，而暂停时物理不 step，
于是"新放的物体和已有物体是否重叠"永远查不到 → 暂停中连点，所有物体落在同一坐标。

顺带还有第二个问题：智能放置的锚点**永远指向目标顶面中心**，
所以同一张桌子上只能放同一个位置的东西（第二个必然与第一个重叠而被拒绝）—— 也就是本轮的问题 2。

两个问题一起解决的办法是**把堆叠判定从物理引擎搬到纯 AABB 数学**：
不依赖物理是否就绪、暂停时也正确、而且快得多。
实测：200 个物体的场景里智能放置建议 **31.8 ms → 1.8~5.9 ms**，单次堆叠判定 **1.87 ms → 0.09 ms**。

## M2 新增了什么

### 真实物理引擎（Rapier 0.21）

- **物理交互遵循现实物理引擎**：接入 Rapier3D，重力 `-9.81 m/s²`、固定步长 `1/60 s`，
  与渲染步分离；暂停时物理完全不推进
- **地形碰撞体是一个 heightfield，不是逐体素立方体**：
  128×128 的地形如果是每格一个碰撞体就是 16384 个，宽相位每次都要过一遍；
  heightfield 只有**一个**碰撞体、一份高度数组，开销与体素数无关。
  实测确认了 Rapier 的约定：`heights[col*(nrows+1)+row]`，**col↔X、row↔Z**，跨度由 `scale` 决定
- **建筑刚体用复合碰撞体**：按模型的每个 part 生成（圆柱/球用真形状，倾斜的用旋转后 AABB），
  所以桌子真的是四条腿站在地上，而不是一个实心方块
- **三种刚体模式**：`static`（稳稳摆着）/ `dynamic`（会掉）/ `kinematic`（被玩家拿着）
- **地形改了就重建**：编辑后防抖 280 ms 重建 heightfield，不会拖着笔刷每帧重建

### 智能放置

- 六个候选来源：**吸附点 / 堆叠 / 贴墙 / 地面 / 网格 / 空中**
- 每个候选都做真检查：地形穿插（体素采样）+ 并列重叠（Rapier 形状重叠查询）+ 支撑（形状投射）
- 打分 = 来源权重 + 稳定性 + 离光标距离 + 是否符合玩家当前朝向；`[` `]` 或点列表切换候选
- **门窗类物件会自动找最近的墙面贴上去**
- 实测：200 个物体的场景里 **10.6 ms** 出结果（验收要求 < 30 ms）

### 堆叠与支撑

- `StackResult` 给出：有没有支撑、支撑物是谁、堆叠层数、接触面积比、重心余量、稳定性三档
- **失去支撑会真的掉下来**：地形被挖掉后 450 ms 内重新判定，悬空的静态物体转成动态刚体自由落体
- 稳定性是**用来说明"为什么"的**，不是真实力学：真实的倾倒交给 Rapier 动态刚体去算

### 选择 / 拿起 / 微调

- 点击选择、`Ctrl` 加选、**拖拽框选**（屏幕矩形投影判交）、全选、选同类
- **高亮合并成一个 LineSegments**：选 500 个物体和选 1 个的 draw call 都是 1 次
- **拿起单个 / 拿起整结构**（相连结构的 BFS 推断，不需要预先分组）
- 拿起时按**光标位移**跟随 —— 不是"把物体中心对齐到光标"，否则抓住的瞬间会跳一下
- 微调：三轴 ±0.25/0.5/1/2 m 平移、±5/15/45/90° 旋转，全部进撤销历史
- 放下时整体校验，不合法就**自动还原**（拖着沙发穿过墙松手时不会卡住，也不会把世界搞坏）

### 分组 / 预制件 / 蓝图 / 镜像

- **分组**：可嵌套、可命名、可跨世界保存；与"整结构"互补（一个是玩家意图，一个是连通性推断）
- **预制件**：选中即存，带**等轴测 SVG 缩略图**（不额外开 WebGL 上下文，几十行算出来的多边形）
- **蓝图**：纯 JSON、带版本与包围盒，可以导出分享、导入放置
- **镜像复制是真镜像**：位置取镜像、绕 Y 取反、**几何体本身也在局部轴上镜像并反转三角形绕序** ——
  少做第三步的话，不对称的模型（书架、汽车）看起来就是错的

### 历史面板与快捷键提示

- 历史面板列出最多 60 条操作（更早的折叠），**点任意一条直接回退/前进到那一步**
- 每组操作带 `group` 名，一次"框选后微调 20 个物体"是一条记录而不是 20 条
- 快捷键速查表 8 组共 56 条，`?` 或 `F1` 开合

### M2 明确**没有**做的（不假装完成）

- **不做建筑破坏**：被砸到不会碎，只是被推开；破坏留给 M3
- **不做结构应力**：支撑判定只回答"能不能放"和"要不要转动态"，
  不是有限元那种应力分布；真实的倾倒完全交给 Rapier
- **不做浮力**：掉进水里会沉到底（水没有体积力），M4 再说
- **不做旋转的 X/Z 微调**：物体可以因为物理翻滚而倾斜，但玩家手动微调只支持绕 Y
- **移动中不做运动学全量同步**：拿起的物体是 kinematic 的，会推开别人但自己不受力
- **物理是异步加载的**：Rapier 的 wasm 有 4.3 MB，所以做成动态导入 ——
  主包先渲染地形（818 KB / gzip 218 KB），物理块（gzip 1.6 MB）后台加载完再接管。
  加载期间的放置会退化成静态摆放，加载完成后自动补上刚体

### M1.5 明确**没有**做的（不假装完成）

- **没有 LOD**：需求里写的是"可选实现、优先保证正确"，本轮把预算花在了剔除与分帧上。
- **没有 Rapier**：M3 的事。建筑是静态放置，不会倒塌。
- **没有阴影贴图**：仍然用"面朝向明暗 + 顶点 AO"来出体积感，手机上更省。
- **地形碰撞体**：M1.5 不需要（没有物理对象落在上面），留到 M3 做整块 cuboid 近似。
- **沙的安息角是离散近似** —— 见下文"物理规则的诚实说明"。
- **水的"半透明"代价**：水和玻璃走独立的半透明几何体，所以**含水的区块是 2 次 draw call**（不含水的仍是 1 次）。

```bash
git clone https://github.com/<你的用户名>/god-sandbox.git
cd god-sandbox
npm install
npm run dev
```

## 笔刷系统

### 5 种形状

| 形状 | 覆盖范围 |
| --- | --- |
| 球形 | 三维球体（默认） |
| 立方 | 正方体 |
| 圆柱 | 立起来的圆柱（高度 = 直径） |
| 平面 | **只影响命中点所在的那一层**，做精细平面编辑 |
| 单点 | 只影响一格，配合密度做"点绘" |

### 12 种模式

| 模式 | 作用方式 | 说明 |
| --- | --- | --- |
| 抬升 / 下沉 | 按列 | 在每列地表上堆叠 / 削掉若干层 |
| 平滑 | 按列 | 高度朝 3×3 邻域平均靠拢 |
| 抹平 | 按列 | 压到笔刷中心列的高度 |
| 顶点捕捉 | 按列 | 把地表吸附到 2 格整数台阶，快速做平台与阶梯 |
| 材质刷 | 按球 | 只换材质不改形状 |
| 挖洞 | 按球 | 挖掉实心方块（**保留水**） |
| 擦除 | 按球 | 什么都清掉（**连水一起**） |
| 填水 | 按球 | 空气填成满格水 |
| 噪声刷 | 按球 | 按三维噪声随机补/挖，做粗糙岩面 |
| 随机刷 | 按球 | 按密度随机散布材质 |
| 边缘软化 | 按球 | 形态学开闭运算：削掉孤立凸块、填上窄缝 |

**强度是小数，怎么做到精细？** 关键在 `stochasticRound`：
强度 0.1、衰减满值时高度增量是 `0.1 × 6 = 0.6` 层 —— 那么这一笔会有 60% 的概率加 1 层、40% 的概率什么都不变。
于是强度滑块真的能"一点点磨"，而不是最小动一整层。

**一次拖动 = 一步撤销**：`BrushSystem.beginStroke()` 在左键按下时开一个事务，
拖动过程中的所有改动都合并进同一个变更集合，抬起时整体交给 `CommandManager`。

## 材质与纹理

- 每种体素都有**独立的顶面 / 侧面 / 底面**图案，用 `DataTexture` 程序化生成（不用外部图片）
- 图案类型：纯色、颗粒噪点、斑点、细点、砖缝、横板木纹、竖纹、草顶、草沿、玻璃网格、水波、
  冰晶、金属拉丝、叶簇、仙人掌棱、熔岩裂纹、大理石纹 —— 共 17 种
- **为什么用 DataTexture 而不是 Canvas**：可以直接把像素写进 `Uint8Array`，
  于是 `npm run verify` 能在 Node 里**真的检查每种体素的贴图有没有图案、顶面是不是绿的**，
  Canvas 版本做不到这一点
- **为什么是图集不是多张贴图**：所有贴图在一张 512×512 图集里，一个区块仍然只有 1 次 draw call
- **顶点级 AO**：每个面角点检查 3 个邻居算遮挡等级，堆叠的方块之间会出现自然暗角
- **描边**：每块贴图四周压一圈暗边 + 左上角提亮，相邻方块之间就有清晰分界
- 右侧「颜色图例」可以展开每种体素的代表色，对照场景认材质

## 物理规则的诚实说明

本轮只做"简化但一致的近似"，**不拟真**。三条规则的实现与局限：

### 水（元胞自动机）

规则：**向下优先 → 向下装不下才向水平更低处扩散**。

- ✅ 水一定有重力，永远会往下走，**不会悬空**
- ✅ 水会被容器托住：四周是实心方块时水就摊平在里面
- ✅ 装满了会从最低的缺口溢出
- ✅ 总量守恒（转移而不是凭空生成）
- ⚠️ 没有压力、惯性、表面张力；流速是人为设的上限（`水速` 参数）
- ⚠️ 一格最多装 1.0，超过的部分靠分给邻居消化，**不是**靠压缩
- ⚠️ 水不会推动物体（M3 接物理后再说）
- ⚠️ 一格水会摊成很薄的一层（没有最小厚度概念），这是元胞自动机的正常表现

可调参数：水速 0.05~1、扩散方向数 1~4、总开关。

### 沙（安息角滑落）

规则：下方是空气就直接掉；否则看斜下方能否滑落。

- ✅ 沙柱会塌成沙堆，不会留下垂直沙墙
- ✅ 沙会填到低处
- ⚠️ **安息角是离散近似**：真正的落沙规则只能产生 45° 堆角。
  本实现用 `slideDistance = 1 / tan(角度)` 决定"滑动前瞻距离"：
  34° → 1.48 → 按概率在"前瞻 1 格（45°）"和"前瞻 2 格（约 26°）"之间混合。
  长期统计下来平均坡度接近设定角度，**但它是两档之间的概率混合，不是连续的精确角度控制**。
  这一点在代码注释里也写明了，不想让人误以为能精确调出 34.0°。

可调参数：安息角 10~60°、总开关。

### 支撑检查（只诊断，不倒塌）

- 从"底部够到地形"的实例出发做 BFS，把相接的实例也标记为有支撑，同时累计水平悬挑距离
- 完全连不上的 → 报告 `floating`；连得上但悬挑超过阈值 → 报告 `cantilever`
- 本轮**只高亮与文字提示，不会真的掉下来** —— 真正的倒塌要等 M3 接 Rapier
- 数据结构已经是 M3 需要的形状（`floating` / `cantilever` 列表直接转动态刚体即可）

可调参数：允许悬挑 1~12 米、总开关。

## 存档

- **格式 v2**：`version / seed / mapId / worldSize / 尺寸 / simTime / camera / settings / chunks / buildings`
- **水量也存**：否则"填满容器"就白做了

## 假设与取舍记录

1. **水的渲染代价**：为了让水面真的有透明感，水和玻璃走独立的半透明几何体，
   于是**含水的区块是 2 次 draw call**。不含水的区块仍是 1 次。
2. **地形不用 InstancedMesh**：需求里提到 InstancedMesh，但它适合"很多个相同的独立物体"。
   体素地形更适合**区块合并网格**（一个区块一次 draw call，且面剔除后三角形数大幅下降），
   所以地形用合并网格、**建筑用 InstancedMesh** —— 各自用在对的地方。
3. **不做 LOD**：需求写的是"可选实现、优先保证正确"，本轮资源投给了剔除与分帧重建。
4. **沙的安息角是概率混合的离散近似**，不是连续精确角度（详见上文物理说明）。
5. **水的 8 位水位**：水量存 `Uint8`（0~255），所以 0.5 实际是 128/255 ≈ 0.50196，
   水面高度会有约 0.4% 的误差。这是刻意换来的：存档体积减半、比较用整数更快。
6. **水流会摊得很薄**：没有最小厚度，1 格水倒进 5×5 的盆会摊成 0.04/格。
   这是元胞自动机的正常行为，不是 bug。
7. **建筑包围盒忽略 rotationX/Z**：车轮、滚筒用了 `rotationX` 放倒，
   但 `instanceBounds` 仍按原始尺寸算（水平方向略有偏差，影响拾取边缘几厘米）。
8. **存档里的参考地图不再重新生成**：载入存档时直接写回体素，而不是重新跑生成器 ——
   这样玩家对参考地图的改造才能保留。
9. **撤销历史不包含水/沙的模拟结果**：模拟改动不计入 `CommandManager`，
   否则撤销会和水流互相打架。撤销只回退"玩家亲手做的编辑"。
10. **Block 上限**：`Uint8Array` 存体素 id，最多 256 种；当前 19 种，M2 追加时**只能在数组末尾加**。

## M2 的假设与取舍记录

1. **地形碰撞用 heightfield，碰撞面是线性插值**：方块地形在物理上表现为"缓坡"而不是台阶。
   这让物体不会卡在方块棱角上（是好事），但也意味着贴地高度与体素表面最多差 ±1 米。
2. **层数统计用包围盒而不是物理投射**：一开始用"反复形状投射 + 排除"实现，逻辑正确但太慢
   （叠在建筑上的候选点单个要 5 ms 以上，8 个候选直接顶到 36 ms，超出 30 ms 预算）。
   换成 O(n) 的包围盒区间比较后降到 10.6 ms，结果对轴对齐堆叠完全一致。
3. **支撑判定是"启发式"不是力学**：`contactRatio` 与 `centerMargin` 的阈值是人为定的经验值，
   目的是让玩家一眼看出哪个摆放不靠谱。真实的倾倒交给 Rapier 动态刚体去算，两者分工明确。
4. **Rapier 动态导入**：wasm 4.3 MB，静态引入会把首屏拖到 5 MB。
   改成 `await import()` 后主包 818 KB，物理块后台加载；加载完成前放置退化成静态摆放。
5. **拿起用光标位移跟随**：早先的实现是"把物体包围盒中心对齐到光标"，
   结果抓住的一瞬间物体会跳一下（墙的中心跑到光标下面）。改成记录抓取时的光标位置、
   后续按位移量驱动，零跳变。
6. **放下失败自动还原而不是拒绝**：拖着沙发穿过墙松手时，原地拒绝会让人卡住；
   自动退回原位体验更好，而且绝对不会把世界搞坏。
7. **镜像做不到"负缩放"而是"镜像几何体"**：`InstancedMesh` 里用负缩放会翻转法线与绕序，
   所以改成给镜像体单独一份几何体（顶点取反 + 索引反序），代价是每个模型多缓存一份镜像几何体。
8. **Kinematic 而不是 Dynamic 的拿起**：拿起的物体被设成 kinematic（自己不受力、能推开别人），
   这样拖动时不会因为碰撞被弹飞；放下时再根据是否有支撑决定转 static 还是 dynamic。
9. **`PhysicsWorld` 只应该有一个活跃的 `TerrainCollider`**：`build()` 只会移除自己上一次建的碰撞体。
   产品里地形是单例所以没问题；如果你要同时挂多个地形，需要自己先 `dispose()` 或 `physics.clear()`。
10. **新增刚体后要等一次 `step()` 才能被查询到**：这是 Rapier 查询管线的固有行为
    （`syncQueries()` 可以手动补一次零步）。产品里靠每帧物理步自然满足。

## M2.5 第一部分的取舍与未做项

1. **堆叠判定不再用 Rapier**：这不是偷懒，是修 bug 的必然结果（见上）。物理引擎仍负责
   "下坠、碰撞、堆叠后的真实稳定"，而"放在哪、能不能放、稳不稳"由 AABB 数学回答。
   两者的分工写得很清楚：`StackingSystem.resolve()` 决定落点，Rapier 决定之后发生什么。
2. **旋转物体用"旋转后的外接矩形"近似接触面积**，不是真实凸包相交。
   对积木式沙盘够用，而且**偏向保守**（只会更容易判成不稳）。
3. **地形接触面积按"高差 ≤ 1 格的列算真正贴上"** 计算，所以斜坡上摆放会自然被判为不稳 —— 这是刻意的。
4. **"抗锯齿"是上下文创建参数，运行时无法真正切换**。质量预设里的 `antialias` 语义是
   "是否允许超采样"，用 `devicePixelRatio`（关时压到 1）表达，不重建渲染上下文。
5. **AO 是烘焙进顶点色的**，所以切换它需要重建全部区块网格（新手世界 9 个区块，第 1 帧就做完）。
6. **自适应降级是"降级容易、恢复难"**：降级需连续 1 秒低帧率，恢复需连续 6 秒高帧率 + 5 FPS 余量。
   这是刻意的迟滞设计 —— 否则画质会随帧率抖动反复横跳，而每次改渲染距离都要卸载/重建区块，反而更卡。
7. **旧存档的尺寸不匹配时不做自动转换**：载入时按存档里的尺寸重建世界（M2 已实现），
   所以老存档仍然能打开，只是世界会回到存档记录的那个档位。**没有实现把体素从一个尺寸重采样到另一个尺寸**。
8. **未做（属于本轮的"其他问题"，留到 M2.5 第二部分）**：地图切换、参考地图房子与树的重叠、
   智能放置的相机追踪。

## M2.5 第二部分修了什么（对照本轮 5 个问题 + 7 条补充）

### 问题 3：参考地图的房子和树重叠

原来的生成顺序是「地形 → 树 → 建筑」，所以房子是**直接长在树上的**，而且房子之间也没查过间距。
现在加了一层 `MapPlanner`（`src/world/MapPlanner.ts`）当"总规划"：

1. **顺序改成 地形 → 水/沙 → 自然物 → 建筑**，每一步都过规划器；
2. 房子先**登记规划区**（`addPlot`），规划区内的树在种下去之前就被拦掉，
   已经在的还会被 `clearNatureInPlots()` 清掉；
3. 自然物之间有**最小间距**（默认 2.5 米），建筑之间有各自的间距；
4. 事后跑一次 `detectOverlaps()` 兜底，扫「建筑体积内的自然体素」与「悬空建筑」；
5. 生成结果输出一份 `MapGenerationReport`：**种了多少、为让位跳过多少、为建房清掉多少、
   建了几个、修了几处重叠、几个悬空、耗时多少**，并在控制台逐行打印、在资源面板里显示。

`npm run verify` 里的实测数据（新手岛 / 山谷村落 / 沙漠绿洲 / 城堡山）：

| 地图 | 建筑 | 自然物 | 为建房清掉 | 让位跳过 | 悬空 | 生成耗时 |
|---|---|---|---|---|---|---|
| 新手岛 | 0 | 4 | 0 | 88 | 0 | 10 ms |
| 山谷村落 | 36 | 55 | 76 | 299 | 0 | 37 ms |
| 沙漠绿洲 | 3 | 70 | 6 | 16 | 0 | 49 ms |
| 城堡山 | 32 | 114 | 0 | 193 | 0 | 23 ms |

> 关于"重叠"的口径：这些地图的建筑是**用零件拼**的 —— 屋顶压在柱头上（实测下沉 0.6 米）、
> 窗嵌在墙里（0.25 米）、墙角两根柱子互相咬合（0.2~0.3 米）。这些是刻意的榫接。
> 所以断言写的是「**没有任何一对零件在三个轴上都插进去超过 0.8 米**」，
> 也就是"没有两栋建筑互穿"，而不是"任何零件都不许接触"。
> 四张图在 0.8 米口径下都是 0 对；零件级咬合对数会打印出来（山谷 4 对、城堡山 2 对，最深 0.60 米）。

### 问题 4：换地图是"叠上去"而不是"卸载"

成因很具体：M1.5 的换图只是「新建一个 World 然后把系统指过去」，旧的 World 从没被拆过，
于是体素数组、区块 geometry、建筑 InstancedMesh、Rapier 刚体、命令历史全都留在内存里。

现在换图的唯一入口是 `Engine.switchWorld()`，流程被拆成有名字的阶段，跑在 `WorldLoader` 里
（阶段之间让帧给进度条，所以"卡住一下"变成"看得见的进度"）：

```
确认（只在真有未保存改动时弹窗）→ 淡出黑幕 → 卸载清单 → 建新世界 → 生成内容
  → 重建物理 → 标记全区块待重建 → 复位相机 → 刷新界面 → 采样对比 → 淡入
```

卸载清单（`src/world/WorldUnloader.ts`）逐条执行、逐条计时、逐条报告，**一条失败不中断后面的**：

1. 解除拾取 / 拿起状态
2. 移除所有建筑刚体（走 Rapier 的 `removeBody`，wasm 侧对象不归 GC 管）
3. 清空物理框架四层（关节 / 触发器 / 逻辑连线 / 组件）
4. 清空 Rapier 世界（刚体 + 碰撞体 + 关节 + 地形 heightfield）
5. 重置地形碰撞体句柄（**必须做**：不然新世界里拿野句柄查询会"撞到空气"）
6. 解绑区块网格 / 释放地形 geometry（GPU）
7. 清空建筑渲染实例 / 隐藏堆叠预览与框选矩形
8. 清空命令历史 / 选择集与分组 / 支撑面索引 / 水与沙的活跃格
9. 体素数据清零（大世界档是上百万格 × 2 份 `Uint8Array`）
10. 复位命中、预览、计数与堆叠工具

**资源监控（补充 4）**：`ResourceMonitor` 每 0.5 秒采一次，给出 JS 堆、Three.js 的几何/贴图/程序数、
体素数据字节数、物理体数。每次换图前后各采一次，算出「释放了多少项、几何/贴图增减、堆增减」并记进面板。
判断泄漏的方法写在面板上：**连续切同一张地图 5 次，「几何」这一列应当回到同一水平**。

诚实说明三条：
- **JS 堆只有 Chromium 内核能读**（`performance.memory`），其他浏览器显示「不可用」而不是 0；
- **显存是粗估**（几何数 × 常量 + 贴图数 × 1 MB），只能看趋势；
- **手动"回收内存"按钮在大多数浏览器上做不到真正回收**：没有 `window.gc` 时它只清掉历史采样，
  并如实弹出「浏览器没开放 GC，真回收要等它自己决定」。不假装成功。

### 问题 5：智能放置看不见落点

1. **脉冲高亮框**（`src/placement/HighlightRenderer.ts`）：绿色可放 / 红色不可放，

### 问题 A：物理框架四层

`src/physics/PhysicsFramework.ts` 把物理按「出问题时该看哪一层」切成四层，每层都有可观测出口：

| 层 | 内容 | 出问题时的症状 |
|---|---|---|
| 第 1 层 · 刚体 | 有哪些东西参与模拟、什么模式 | 东西不动 / 乱飞 |
| 第 2 层 · 碰撞 | 形状（本项目用模型零件拼复合碰撞体） | 穿模 |
| 第 3 层 · 约束 | 6 种关节（固定 / 旋转 / 滑动 / 球窝 / 绳索 / 弹簧） | 该连着却散开 |
| 第 4 层 · 逻辑 | 触发器 + 逻辑连线（事件 → 动作） | 拉了没反应 |

- **6 种关节**都走 Rapier 0.21 的原生求解器（`rope` 与 `spring` 都存在，不用自己施力）。
  实测确认的两个坑：① 0.21 **没有** `setMotorVelocity`，电机要用 `setMotorMaxForce` +
  `configureMotorVelocity`；② 本项目的 wasm 构建会把 u32 handle 的位模式当 f64 交回 JS
  （第 2 个刚体 handle 是 `5e-324`），所以「字符串 ↔ 句柄」一律 `String()` / `Number()`，
  **绝不能用 `parseInt`**（它会把 `5e-324` 读成 `5`，关节就接到完全无关的物体上）。
- **组件是纯数据**（`PhysicsComponent`），不是行为对象：能直接进存档，也能在 Node 里断言。
- **逻辑连线纯逻辑、零依赖**：`LogicLink` 只返回「该做什么」，真正的副作用（震手机、弹提示、
  删建筑、生成物体）集中在 `Engine.executeLogicAction()` 一处，所以第 4 层可以在 Node 里单测。
- **调试可视化**：关节连线 / 绳索松弛长度 / 触发器盒子 / 逻辑箭头 / 碰撞盒 / 只画线框，
  全部合批进**一个** `LineSegments`（逐个建对象会让 draw call 翻十倍）。

### 第 5 批：20 个物理组合 + 3 个教学关卡

- `src/data/combos.ts`：20 个**已经接好关节**的成品（会开的门、会转的风车、投石机、摩天轮…），
  共 64 个零件 / 46 个关节，覆盖 5 个分类。玩家不用调任何参数就能看到物理效果。

  ① 句柄字符串化（见上）；② **物理没就绪时关节进待建队列**，就绪后自动补建（不是失败）；
  ③ 组合整体旋转时锚点要**既旋转又平移**（漏掉平移的症状是"关节在离物体很远的地方凭空拉住它们"）。

### 问题 B + 第 6~7 批：移动端

`src/mobile/MobileController.ts` 把六件事收在一处（手势、设备探测、屏幕方向、双摇杆、震动、手势教学）：

| 手势 | 行为 |
|---|---|
| 单指拖动 | 光标跟随手指（瞄准），**不动镜头** |
| 单指轻点 | 在光标处放置 / 选择 |
| 单指长按 | 瞄准 + 选中 + 拿起 |
| 单指双击 | 取消当前放置 |
| 双指开合 | 缩放 |

- **为什么单指拖动不转镜头**：瞄准和转视角用同一个手势的话，玩家永远对不准想要的那一格

- **手势教学（补充 6）**：只在触屏设备、且以前没学过时自动弹一次；不阻塞操作

- **移动端布局**：`body.touch-device` / `body.mobile-portrait` / `body.mobile-narrow` 三档 class，
  窄屏隐藏调试类面板、所有按钮 ≥ 44×44、状态条避开手势条安全区。

## M2.5 第二部分的取舍与未做项

1. **两个已知缺口（必须说清楚）**：
   - **存档里不含关节 / 触发器 / 逻辑连线。** 存档存的是建筑**实例 id**，而关节两端在 Rapier 里是
     **刚体 handle**，读档时刚体会全部重建、handle 全变，所以需要做「id ↔ handle」双向映射与重连。
     这是一个独立的小课题，仓促做只会做出"读档后关节连到随机物体上"的更糟结果。
     **但绝不静默丢数据**：保存时如果世界里有关节/触发器/连线，会明确弹出提示告诉玩家读档后要重新摆。
   - **没有关节 / 触发器的可视化编辑器。** 现在玩家只能用现成的 20 个组合，
     还不能自己"点两个物体 → 接一个铰链"。数据层（`jointTypes.ts` / `physicsComponents.ts`）
     和系统层（`JointSystem` / `TriggerSystem` / `LogicLink`）都已经就绪，缺的是那两块 UI。
2. **`Tab` 与 `P`/`G` 的键位冲突教训**：第一次实现时我把组合面板放在 `P`、物理面板放在 `G`，
   结果把原有的「暂停」和「吸附点对齐」悄悄覆盖了 —— `vite build` 只给一句警告，跑起来就是功能失灵。
   最终键位：组合 `K`、教学 `J`、物理面板 `F2`，且用脚本检查过同一 switch 内没有重复 case。
3. **穿模断言的口径**（见问题 3 上方说明）：把阈值定在 0.8 米而不是"碰到就算"，
   是因为零件级榫接是刻意的，一个永远红着的检查等于没有检查。
4. **移动端摇杆驱动机器而不是角色**：本项目没有玩家角色，所以摇杆驱动的是**相机**。
   这不是退让，而是"沙盘模拟器"这个题材本来就没有第一人称角色。
5. **设备评级是启发式**：`deviceMemory` / `hardwareConcurrency` 在 iOS 上基本读不到，
   所以拿不到就按核数和 DPR 推断，并在面板上把**理由**写出来（例如
   「4 核 / 4GB 内存 / DPR 3 → 低配：关阴影、关渲染距离 4」），玩家能自己判断合不合理。
6. **`ResourceMonitor` 的显存是粗估**、**JS 堆只有 Chromium 能读**：这两条都在面板上写明，
   不把估出来的数字当真值展示。
7. **未做（留到下一轮）**：物品库从 77 补足到 120+、关节/触发器编辑器 UI、
   存档携带物理连线、把物理调试可视化扩展到"接触点与受力箭头"。

## M3 已落地部分（第 1~2 批 + 部分第 7~8 批）

### 1. Rapier 世界生命周期（`src/physics/RapierWorld.ts`）

把"世界"从"刚体管理"里拆出来，成为唯一的所有者：加载、配置、清空、销毁、统计。
拆的理由是 M2 把两者混在一起，导致**重力/时间步/求解迭代这些世界级参数从来没有被重新应用过**，
而 M3 要求它们全部可调（5 个行星预设、时间流速、慢速档）。

**加载进度做成了两种模式，并且如实标注是哪一种**（面板上直接写出来）：

| 模式 | 什么时候用 | 数据来源 |
|---|---|---|
| `bytes` | 构建时给 rapier 的 chunk 固定了文件名（`vite.config.ts` 的 `chunkFileNames` → `assets/rapier.js`） | `fetch` + `Content-Length` + 流式分片读，**真实字节百分比** |
| `phases` | 拿不到固定 URL / fetch 被拦 / 离线 | 四个已知阶段（下载 → wasm 实例化 → 建世界 → 就绪）的**阶段权重**，界面上写「拿不到字节进度」 |

代价写在配置注释里：`assets/rapier.js` 不再带内容 hash（靠 HTTP 缓存头验证），换来的是加载时看得见的真实进度。

**加载失败不等于启动失败**：地形、笔刷、建筑摆放、存档都不依赖 Rapier，
所以失败时明确告诉玩家"沙盘仍可使用，但没有重力与碰撞"，而不是白屏。

顺带修掉一个 M2 留下的隐蔽 bug：`syncQueries()` 把 `world.timestep` 设成 0 之后**没有恢复**，
当时能正常工作纯粹是因为每帧的 `step()` 都会重新写一遍时间步，把这个坑盖住了。
M3 起时间步可配置，这种"靠别人擦屁股"的写法不能留，所以改成保存/恢复，并写进注释。

### 2. 区块级地形碰撞体（`src/physics/TerrainCollider.ts` 重写）

| 区块形态 | 用哪种碰撞体 | 理由 |
|---|---|---|
| 列实心（每列从底到顶连续） | **一个 heightfield** | 高度图对这种地形是**精确**的，而且只有一个碰撞体，最省 |
| 有洞穴 / 悬挑 / 中空 | **greedy 合并的若干 cuboid** | 高度图会把空洞填实 —— 表现是"看得见洞、走不进去" |

- **局部更新**：改一格体素只重建那**一个区块**的碰撞体。M2 是全世界重建整张高度图
  （标准档 9216 个采样点、大档 3.7 万点），这是编辑卡顿的来源之一。
  单帧最多重建 6 个区块，避免大面积编辑时一帧卡住。
- **所有区块的碰撞体挂在同一个静态刚体上**：`Engine` 与 `BuildingSystem` 都依赖
  `bodyHandle` 识别"打到的是地形"并当作建筑的静态锚点，每区块一个刚体会让这个 handle
  变成列表、要改动一堆既有代码；而 Rapier 允许在一个刚体上挂任意多个碰撞体，
  局部更新只要 `removeCollider + createCollider`，刚体本身不动。
- 贪心合并（`greedyMerge`）是三维的（先沿 X、再沿 Z、再沿 Y 扩），
  一块 16×16×8 的实心地形从 2048 个碰撞体降到十几个。`MAX_BOXES_PER_CHUNK = 96` 是安全阀。

### 3. 碰撞分组与碰撞矩阵（`src/physics/ColliderFactory.ts`）

M2 所有东西都在默认分组里，于是有三个真实问题：触发区把地形一直算成"里面有东西"、
水体如果参与碰撞会像砖头一样挡住物体、拿起物体时它和脚下支撑面互相挤压产生抖动。
现在明确分 5 层（地形/建筑/物体/水体/触发器）并给出一张矩阵：

| 层 | 作用对象 |
|---|---|
| 地形 | 建筑、物体 |
| 建筑 | 地形、建筑、物体、触发器 |
| 物体 | 地形、建筑、物体、触发器 |
| 水体 | **无**（浮力靠每帧施力，不靠碰撞求解 —— 否则物体掉水里会像撞到凝胶一样停住） |
| 触发器 | 建筑、物体（只报事件，不产生碰撞响应） |

编码是 Rapier 的约定：高 16 位 = 成员层，低 16 位 = 过滤器。`layersOf()` 能反解出来给调试面板看。

### 4. 六种碰撞体形状的取舍

`cuboid` / `ball` / `cylinder` / `capsule` / `convexHull` / `trimesh`。
两个必须说清的取舍：
- **带腿的家具不用凸包**，而是多个 `cuboid` 组合。凸包会把椅子腿之间的空隙填满，
  于是"能从椅子底下钻过去"这件事没了。
- **`trimesh` 只用于静态**（Rapier 的硬限制）。代码里直接拦下动态 trimesh，
  并在凸包退化（顶点不足 4 个或共线）时自动回退成包围盒并记告警 —— 宁可粗略，也不能没有碰撞体。

### 5. 刚体工厂（`src/physics/RigidBodyFactory.ts`）

四类刚体（fixed / dynamic / kinematicPosition / kinematicVelocity）+ 质量、阻尼、休眠、重力缩放、CCD、
锁定轴。两个刻意的决定：

- **参数优先级只有一处实现**：`resolveBodyParams()` 里写死「spec 显式值 > 材质值 > 全局默认」。
  只要有任何一处绕过它去直接读材质的某个字段，"改材质没生效"这类问题就会重新出现。
- **没有碰撞体的刚体一律拒绝创建**。那种物体看得见、穿得过，还会出现在统计里让人以为物理正常 ——
  是排查成本最高的一类"幽灵"。返回值里带中文原因，调用方直接能提示玩家。

### 6. 材质运行时（`src/physics/PhysicsMaterial.ts`）

数据层（8 种预设 + 合并规则）之外的运行时：材质覆盖单独存 `ownerId → materialId`，
**不塞进 `BuildingInstance`**（否则建筑存档被迫理解物理概念，而且复制物体时材质会跟着复制）。

换材质必须同时改三个地方，少一个玩家就会觉得"材质系统是假的"：
1. 碰撞体的 `friction` / `restitution` / `density`（Rapier 允许运行时改，质量会立刻重算）；
2. **刚体**的 `linearDamping` / `angularDamping`（阻尼在刚体上，不在碰撞体上 —— 最容易漏的一步）；
3. **唤醒刚体**（睡着的东西不会用新参数，表现是"改了材质但没变"）。

### 7. 时间倍速与位姿回溯（第 6 批核心）

**倍速靠改缩放、不改步长。** 4 倍速做成"把时间步改成 1/240"是错的：物理行为依赖时间步，
会出现"同样一堵墙，1 倍速不倒、4 倍速倒了"。正确做法是保持 1/60、每帧推进更多子步。
慢速档（0.5 / 0.25）同理 —— 那是观察碰撞过程最有用的档位，一颗球落地的那一帧在 1 倍速下根本看不清。

**回溯记录位姿，不存世界快照**（理由见下），300 帧缓冲 ≈ 7.7 MB：

| 方案 | 300 帧体积 | 恢复语义 |
|---|---|---|
| `world.takeSnapshot()` | 几十 KB ~ MB / 帧 → **几十上百 MB，手机会崩** | **`restoreSnapshot` 是静态方法，返回新世界对象** → 所有刚体 handle 失效 |
| 位姿（本项目采用） | 7 float/刚体，800 刚体 × 300 帧 ≈ **7.7 MB** | 写回位置 + 四元数，并**清零速度** |

位姿方案唯一的代价是**不重算接触力**（接触点是求解器的中间量），所以回溯后物理读数要等再跑一步才准；
这一点在 UI 与 README 里都写明了，不假装是完整状态回放。

三个容易漏的细节：
- **写回必须清零速度**：只改位置不改速度的话，物体回到历史位置后会带着当前速度继续飞；
- **世代号**：换地图后 handle 全部重分配，旧帧必须能被识别并拒绝，否则一按回退就把新世界的物体
  传送到旧世界的位置上，看起来像物理彻底坏了；
- **回溯期间物理一步都不推**（`TimeControl.advance` 直接返回 0），否则历史位姿与实时模拟会互相打架。

### 8. 已接线与未接线

**已接进 Engine**：四个面板（物理参数 / 时间轴 / 应力 / 物理教学）、刚体工厂、材质运行时、
时间控制、位姿回溯、爆炸保护、录制器、合成音效、物理教学状态机。
按 `R` 回溯一帧（`Shift+R` 前进），`Shift+B` 重建全部网格，`Ctrl+Shift+R` 重新生成地形。

**唯一未完成项：浏览器端实机验证。** 这台手机上无障碍服务没开，截屏与读屏都用不了，
所以全部 UI 与渲染效果只经过了 `tsc` + DOM id 静态核对 + 子代理的 jsdom 冒烟，
**没有真跑过浏览器**。任何"看起来应该没问题"的渲染代码都需要你实际打开页面确认一次。

另外两项已知的近似（不是缺失，是刻意的取舍，都写在对应模块的头部注释里）：
- `StressVisualizer` 的接触点数用的是接触点数代理（要接真实接触报告需要开 `CONTACT_FORCE_EVENTS`）；
- 音效用 Δv（速度变化量）当撞击强度代理，不是真实接触冲量。

### 9. 浮力（`src/physics/BuoyancySystem.ts`）

**水不做碰撞体，只施力。** 给水建碰撞体的话，物体掉进水里会像撞到凝胶一样停住 —— 那不是水。
所以做法是：元胞自动机照旧算水，浮力系统每帧给水里的动态物体加力。

浮力用教科书式 `F = ρ·g·V_排水`，"木头浮、石头沉"完全来自**材质密度与水的比较**（650 < 1000 浮；
2600 > 1000 沉），没有别的魔法。**四条要写清楚的近似**：

1. **排水体积用 AABB 算**：中间挖空的船，AABB 排水量远大于真实船体。所以本项目的"船能浮"
   靠的是"我们按盒子算"，不是"我们模拟了船体"；空心与实心的差别只体现在材质密度上。
2. **不做姿态力矩**：真实浮力作用在浮心上，会让倾斜的船自己扶正。这里只在质心加向上合力，
   所以**一条侧翻的木头不会自己翻回来**。
3. **阻力是线性的**（`-k·v`，和 Rapier 阻尼同形式）：好处是数值稳定，代价是快速入水没有真实减速感。
4. **水面高度是由"淹了多深"反推的估计值**，不是真的找到水面 —— 完全没入时真实水面在物体上方，
   我们无从得知（也不需要知道）。

第一版实现是"从物体顶往下找第一个有水的高度当水面"，结果是**一个完全没入的 1 立方米木头只算出
0.83 m³ 的排水量**，于是浮力略小于重力、本该浮的木头会缓慢下沉。改成**沿高度逐层积分**后
完全没入精确等于全高 —— 这种"差一点点"的 bug 最难发现，写在这里备查。

### 10. 局部倒塌（`src/physics/CollapseSystem.ts`）

**"局部"是重点。** M2 的做法是"所有失去支撑的物体一起转动态"，问题是连坐（挖掉塔底一块砖，
旁边没关系的东西也跟着掉）且玩家反应不过来。M3 改成：**从地基出发做连通性标记，
只有跟地基断开的那一块才倒**，而且有 **600 毫秒宽限期**（先提示"有 N 个物体失去支撑，马上会掉"）。

判定口径按你之前的裁决：**AABB 数学是权威**（任何时刻都有效，包括物理暂停时），
**Rapier 接触力做校核**（`reconcile()`：AABB 说断了但 Rapier 报出支撑力 → 救回来，并记日志；
接触点只有 1 个 → 改判临界）。两个阈值按你给的：**悬挑 > 尺寸的 50%**、**接触面积 < 底面积的 30%**。

贴合判定刻意**宽松**（15 厘米容差）：判太严会让玩家看到"明明挨着的两块砖，上面那块却掉了"，
那比偶尔把一块悬空的砖算成稳的更像 bug —— 后者还有 Rapier 接触力兜底。

### 11. 应力可视化（`src/physics/StressVisualizer.ts`）

⚠️ **这不是有限元分析**，面板与 README 都照这个口径写：

```
应力 ≈ 0.55 × (1 − 支撑充分度) + 0.30 × 承重比例 + 0.15 × 悬挑比例
```

它能回答"我这座桥看起来合理吗"，**不能**回答"这根梁 3.2 秒后会不会断"。
真实应力要解弹性力学方程，那需要一整套求解器，与"纯前端 + 手机上 30 FPS"直接冲突。

着色复用 `instanceColor` 通道（**不额外开 draw call**），并且低应力必须是**纯白**（不染色）——
否则整座建筑变成一片颜色，反而看不出哪里危险。它与稳定性着色**互斥**（同一条通道两种语义），
面板上写明了。

### 12. sensor 触发器与逻辑门（第 4 批）

**触发器从"盒查询轮询"改成 Rapier sensor。** M2.5 的轮询有三个真毛病：

| 毛病 | 后果 |
|---|---|
| 形状只能是盒子 | 玩家画半径 2 米的圆形感应区，实际在 2.8 米的角落也触发 |
| **会漏掉快速穿过** | 20 m/s 的物体 100ms 走 2 米，轮询完全可能一次都没采样到 |
| 每帧都要问"谁在里面" | 500 个物体 × 若干触发区的持续开销 |

sensor 是求解器的一部分：**不会漏**，而且只在状态变化时才产生事件（静止的世界零成本）。
代价是 Rapier 只给 begin/end —— **`stay` 是我们自己按 200ms 节流补发的**，这一点在面板上写明了。

一个必须记住的坑：**`world.step(eventQueue)` 是事件产生的唯一时机**，而 `step()` 只被世界管理器调用。
所以事件队列必须由 `RapierWorldManager` 持有 —— 让 TriggerSystem 自己建一个队列，
它拿到的永远是空的（代码看起来完全正确但永远不工作）。

**逻辑门**（第 4 批新增），每一种的语义都写成可判定的：

| 门 | 语义 | 关键参数 |
|---|---|---|
| 直接 | 事件到 → 立刻执行 | — |
| 或 | 任一输入触发 | — |
| 与 | 窗口内凑齐 N 个输入才执行一次，触发后清空（否则按一次触发一片） | `required`（2）、`windowMs`（400） |
| 非 | 抑制源在窗口内**没有**活动才执行 | `inhibitSourceId`、`windowMs` |
| 延时 | 排队等 N 毫秒再执行（**排队不丢弃**，连按两次会执行两次） | `delayMs`（500） |
| 计时 | 持续活动时每 N 毫秒执行一次（踩住压力板 → 机关每秒钟转一圈） | `intervalMs`（1000）、`windowMs` |

`validate()` 会把"等于没设门"的配置当成错误报出来（没有抑制源的非门、延时 0、
要求 1 个输入的与门、周期小于 50ms 的计时门）—— 一个永远为真的非门是逻辑错误，不该静默生效。

**第一版踩的坑写在这里备查**：`LogicLink.add()` 是**逐字段构造**记录的（不是展开 spec），
我加了 `gate` 字段却忘了在 `add()` 里拷一行，结果**门配置被静默丢弃、全部退化成直接触发**
（9 条断言同时红）。同类问题在 `clear()` 上也存在：门的运行时状态是按连线 id 存的，
而 id 从 1 重新开始，不清就会串到新世界的连线上。

### 13. 关节与马达（第 3 批）

**马达有两种模式，它们的区别不是实现细节，而是玩家感知到的行为完全不同**：

| 模式 | 行为 | 典型用法 |
|---|---|---|
| `velocity` 速度驱动 | 一直以目标速度转/推（需要一个行程限位去挡住它） | 轮子持续转、传送带 |
| `position` 位置驱动 | 用弹簧-阻尼模型走到目标角度并**停在那里** | 门"开到 90° 就停"、活塞伸到 0.5 米 |

Rapier 0.21 的 API（实测确认，不是猜的）：`configureMotorVelocity(targetVel, factor)` 与
`configureMotorPosition(targetPos, stiffness, damping)`，加上共用的 `setMotorMaxForce`。
**没有 `setMotorVelocity(speed, maxForce)`** —— 照那个签名写会得到 `undefined is not a function`，
而且只在真的建关节时才暴露。

`JointFactory.ts` 承担"参数怎么理解"这件事（类型是否支持、缺省、越界、告警），
因为全是边界条件，必须能在 Node 里断言。一个刻意的决定：**Rapier 不支持位置驱动时如实失败，
不退化成速度驱动** —— 退化的表现是"门关不上，一直在转"，比直接失败更难排查。

**关节编辑器**补上了 M2.5 留下的缺口（数据层与系统层早就就绪，但玩家没法自己接铰链）。
两个设计细节：
- **轴用三个数字输入而不是 X/Y/Z 按钮**：吊桥的轴经常是斜的，三个按钮表达不了；
- **单位必须写在界面上**：旋转关节的位置是**弧度**、滑动关节是**米**。
  不写清楚的话玩家输入 90 会以为门开 90 度，实际会把限位推到 90 弧度（≈ 14 圈）。

**限位可视化**：调试绘制里，旋转关节在锚点处绕轴画一段圆弧（8 段折线）表示"能转到哪"，
滑动关节沿轴画一条从 min 到 max 的线段。没有限位的关节不画 ——
画一条"无限的线"没有意义，只会让画面糊掉。

### 14. 物理调试可视化（第 6 批）

`PhysicsDebug.ts` **只做数据、不做渲染**：Engine 负责跨 wasm 边界读接触对，
它负责把接触点/法线/速度翻译成可画的几何。这样"接触点画在错的位置"这种
在浏览器里肉眼很难发现的问题，可以在 Node 里用假数据断言。

**四条可视化各自的诚实边界**（都显示在面板上）：

| 可视化 | 准确的部分 | 不准确的部分 |
|---|---|---|
| 接触点 | 位置与数量来自求解器真实的 solver contact | 只画当前帧还在的接触，分离瞬间就没了 |
| 接触法线箭头 | **方向**物理准确（指向分离方向） | **长度不是牛顿数** —— 按穿透深度与接触点数缩放的相对量 |
| 速度向量 | 方向与相对大小准确（1 m/s = 0.25 米） | 为可读性做了缩放，不是 1:1 |
| 休眠着色 | 休眠状态就是 Rapier 的真实状态 | 与稳定性着色**共用 instanceColor 通道**，会互相盖住 |

**为什么它叫"接触法线箭头"而不是"受力箭头"**：Rapier 的 JS 绑定没有暴露每个接触点的**冲量**
（那是求解器内部的 λ）；要拿真实的力必须开 `CONTACT_FORCE_EVENTS`，而那给的是**整对碰撞体的合力**、
不是每个接触点。所以这里只画方向 + 相对长度，并如实命名 —— 叫它"受力"会让人以为长度就是牛顿数，
进而得出完全错误的结构结论。这句话作为常量 `DEBUG_DISCLAIMER` 写在代码里，
保证它每次随着可视化一起出现。

性能取舍：接触读取只遍历**相机 40 米内的最多 120 个动态物体**（扫全世界在 500 个物体时
每帧要问 500 次），实测几何收集在「64 接触对 + 120 刚体」下 **1.88 ms**，
测试里带 2 ms 的回归门。全部调试项与新增的点云共用**2 次 draw call**（1 个 LineSegments + 1 个 Points）。

顺带修掉一个真问题：`index.html` 里 `data-physics-debug="colliderBoxes"` 出现了**两次**
（重复的开关），断言把 html 的开关清单与代码键名做了逐字比对才抓到 ——
少一个开关或名字写错，表现都是"面板上有这个选项但没作用"。

### 15. 距离剔除与分帧调度（第 7 批）

**先说清楚"物理 LOD"在本项目里不是"远处换简单碰撞体"。** 那条路在 Rapier 里是负优化：
改碰撞体形状必须删旧的、建新的，而删建要更新宽相位、重算质量与惯性张量 ——
物体在远近来来回回时，这项开销比"远处那点求解成本"大得多。

所以物理 LOD 用的是**参与度降级**：

| 档位 | 条件 | 做法 | 代价 |
|---|---|---|---|
| 完整模拟 | 相机 24 米内 | 什么都不做 | 无 |
| 自然休眠 | 静止 2 秒（Rapier 自己做） | 求解器跳过 | 无 |
| **冻结** | 已休眠**且**离相机 60 米外 | `setEnabled(false)` | **它不再碰撞** |

**冻结的代价必须写出来**：`setEnabled(false)` 的刚体不参与任何碰撞 —— 远处一块被冻结的石头，
有东西飞过去砸它会直接穿过去。这不是 bug，是功能的定义。两条硬规则把它限制到"几乎看不到"：
① **只冻结已经在休眠的物体**（半空冻住是最显眼的穿帮，物体悬在空中不动一眼就看得出来）；
② **重要物体永不冻结**（选中的 / 手里拿的 / 连着关节的 / 稳定器锁定的）。
唤醒是**立即的、不分帧的**（漏一帧就是穿模），只有冻结分帧。

**分帧调度**解决的是一件很具体的事：倒塌判定（BFS 是 O(n²)）、应力计算、距离剔除、
支撑面索引这几件周期性重活原来各按各的固定间隔跑，于是**会周期性撞在同一帧** ——
帧时间从 6ms 尖到 20ms，表现是"每隔半秒卡一下"，比平均帧率低更难忍。
现在它们共用一个每帧 2.5 ms 的预算，到期的任务按"优先级 → 越久没跑越优先"排序，超预算的推到下一帧。
总工作量不变但摊平了，代价是某个任务偶尔晚一帧。

两个刻意的设计：**所有任务共用同一个时间源**（调用方传入，任务自己不读时钟，
否则测试里没法复现调度顺序）；**任务抛异常只影响它自己**（一个坏任务让调度器停摆，
会让所有周期性维护静默失效，比报错更难查）。

### 16. 压力测试场景（第 8 批）

3 个场景（500 箱塔 / 100 齿轮传动 / 50 吊桥）的数据在 `data/stressTestMaps.ts`，
生成器 `world/StressTestGenerator.ts` 把数据变成建筑 + 刚体 + 关节。

两个关键行为：
- **手机一律降级**（500 → 120 等），而且**在生成之前就决定**，不是生成到一半发现超限；
  按钮文案里就写明"将生成多少个"，点下去才发现和预期不一样是没法接受的。
- **它会清空当前世界**（几百个刚体不可能叠加到现有世界上），所以走的是和换地图
  **同一条卸载路径**（`WorldRequest` 加了 `kind: 'stress'`）——
  多开一条独立路径就多一处内存泄漏的机会。UI 上把这件事写在按钮旁边。

超过动态上限的物体**退化成静态并记账**（`degradedToStatic`），不静默降级 ——
静默降级会让玩家以为"物理坏了"。

### 17. 拖拽连线 UI（第 4 批收尾）

**三步，每步都有界面反馈**：① 在视口里按住一个物体 → 拾取为源，画一条跟随光标的虚线；
② 拖动 → 覆盖层颜色随"光标下有没有合法目标"变绿/变红，文案变成"松手连到「木门」"；
③ 松手 → 预填两端，玩家选**事件**与**动作**后点「建立连线」。

**为什么松手后还要点一下**（而不是拖完自动连）：一条连线至少需要"监听什么事件"与
"执行什么动作"，而拖拽只表达了"从谁到谁"。硬要自动连就必须猜一个默认事件/动作，
猜错的后果是玩家得到一个自己不想要的连线 —— 那比多点一下烦人得多。

连线用 **SVG 覆盖层**画而不是在 3D 场景里画：屏幕空间的连线本来就该是屏幕空间的 ——
它表达的是"这两个东西之间的连接"，不是空间中的一根绳子。3D 里画还要每帧反投影（近平面附近会数值爆炸），
而且线宽会随距离变细到看不见。

**第一版踩的两个坑（都写进注释备查）**：
1. 我把 `linkSpecFromConfig` 当成了"编辑器 → 逻辑层"的桥，其实它是**组合数据**的桥
   （事件 → 固定配套动作的映射表）。误用它的后果很具体：**玩家选了"驱动马达"，
   实际建出来的是弹提示**，而且映射表对未登记的事件返回 undefined，动作会被静默丢弃。
2. `matchesSource` 只比对 `event.target` 与 `data` 里的几个字段，**没有 `triggerOwnerId`** ——
   于是"给按钮建一条连线"永远匹配不上：按钮不动，动的是踩它的人。
   现在事件里带上了触发区绑定的宿主，比对也认这个字段。

**非门仍然不可配**（它需要"抑制源"这个第二参照物，拖拽只能表达两个端点）。
这一点在面板上写出来并给了替代方案，而不是放一个选了也没用的选项 ——
断言里专门校验了"被排除的门必须有中文原因"。

## M4 第一部分的取舍（按约定逐条记录）

1. **不做遮挡剔除**（需求里标了"可选"）。体素地形上的遮挡剔除要软件光栅化一张深度图（或硬件遮挡查询），
   那是独立的大课题；而本项目的瓶颈实测在"区块网格重建"与"物理求解"，不在这条上。
   预算给了距离剔除与分帧调度。
2. **不做 Service Worker**。项目部署在 GitHub Pages 的子路径 `/god-sandbox/` 下，SW 的 scope 与
   "改了代码缓存没更新"是经典坑；改为"资源按需分包 + 物品库懒加载"，Pages 自带 CDN 与强缓存已经拿到大半收益。
3. **生成回滚只回滚"参数 + 种子"**，不保留体素副本：大世界档保留两份 `Uint8Array` 会吃上百 MB。
4. **热力图用顶视图 canvas**，不做 3D 贴图：简单、够用、手机上也不卡。
5. **内容包按一级分类划分**，不另立一套标签：分类已存在、已被存档与断言引用，
   再建平行体系必然出现"某个物品属于哪个包"说不清的情况。
6. **Player 自定义物品不能上传模型、不能自定义碰撞体形状、不能加新的物理组件类型** ——
   纯前端没有模型解析器与付费存储；组件类型是代码里的枚举。自定义的范围是"用基本几何体拼一个东西"。

## M4 第二部分的取舍续记（同一轮的补记，逐条记录）

7. **冲突检测**搬进了 Web Worker，但**流水线阶段 9 仍然走主线程** —— 这是实测结论，不是偷懒。
   实测（`plain_village` 真实流水线产物，热身后 10 次平均）：

   | 世界档 | 打包地形快照（主线程） | 纯检测（主线程） |
   |---|---|---|
   | 新手 48×16×48（92 物体，0.11 MB 快照） | 1.6~2.7 ms | 1.8~3.4 ms |
   | 大型 192×32×192（718 物体，2.96 MB 快照） | 30~40 ms | 17.7~20.5 ms |

   **光"打包快照"就不比检测本身便宜**，大档净亏 10~20 ms，worker 侧还多烧 130 ms 的 CPU。
   所以 `ConflictRunner` 保留为"结果与同步路径逐字一致"的**可用能力**（47 条断言覆盖，含
   "Node 下如实走主线程回退、不把回退报成 worker"），等快照搬运量降下来（列级快照或
   worker 侧缓存地形）再接进流水线。**"用了 Worker"这句话本身不是目的，主线程变快才是。**
8. **同一个"构建单元"内部的相交不算冲突**：一栋房子是拼出来的（墙压地板、屋顶搭墙），
   那种相交是设计本身。第一版没有 `owner` 字段，7 栋房（91 个构件）自己跟自己报出上百处
   "重叠"，修复器反复挪又挪不动，日志留下"189 处未解决"——看起来像生成失败，其实是检测口径错了。
   **一个错误的检测器比没有检测器更糟：它会让人去"修"本来正确的东西。**
9. **树间距按树冠半径算，不写死 3 米**：阔叶树树冠直径 4.2 米，间距 3 米必然互相穿进去
   （实测 391 处重叠冲突，绝大部分是树冠 vs 树冠）。这件事**不能靠放宽容差掩盖** ——
   容差一放，建筑与物品的真实重叠也一起被放过了。改在生成规则里解决：
   `间距 = max(类别下限, 树冠半径 × 2 × 0.95)`，系数不到 1 是刻意的（完全不让碰会像人工林）。
10. **自然物在生成时就按模型半尺寸内缩**，不留给冲突修复去挪：贴着世界边缘生成的树，
    树冠会探出边界（实测 11 处 `outOfBounds`），而边界上的树**挪哪儿都还在边界**。
11. **Worker 结果只覆盖"快照那一刻"的地形**：主线程在等回包期间改了地形，结果会与"此刻同步调用"
    有差异（阶段 9 不写世界，实践中一致）。协议里不含水位数据（检测器不读水位），
    将来检测器一旦开始读水位，协议必须同步扩展 —— 这条写在 `conflictWorkerCore.ts` 顶部。
12. **生成预览是降采样近似**，画布右下角标着"近似预览 · 非真实体素"。`PreviewData.limitations`
    至少 5 条中文事实：小物品与门洞的冲突看不出来、洞穴/悬垂处不准、不跑物理、
    只跑了阶段 1~4 + 规划与撒点、冲突修复还可能再删树。预览**复用**真实生成的高度图函数与
    `BuildingPlanner.plan()`，没有第二份噪声实现（唯一抄下来的是规划阶段那两条倍率公式，
    因为原方法是 private，注释里标了"那边改了这里要跟"）。
13. **生成回滚只回滚参数与种子**（与第 3 条一致），按钮下面写着这句小字。
    面板只能记"点生成时提交的参数"，**确实成功的那一份由 Engine 在生成成功后纠正**。
14. **冲突可视化画的是标记不是重叠体积**：框的边长是 0.6 米 × 严重度系数，
    真实相交尺寸只在 `ConflictRecord.detail` 的文本里，而且那也只是轴对齐包围盒的相交尺寸。
    标记上限默认 400 个，超出部分**如实报告**（`stats.skipped`）而不是静默丢弃。
15. **内容统计热力图用俯视 2D canvas**，坐标原点必须传世界的 `originX/originZ`：
    世界是以原点为中心的，只按 `[0, sizeX)` 分箱会把左半边全夹进第 0 列 —— 那张图比没有图更糟。
16. **内容包有"关掉只隐藏、不删世界里的物体"这一条硬语义**，两个入口（物品面板内联开关 +
    设置区面板）读同一个存储键，任一边变化都会刷新另一边（`CatalogPanel.reloadPacks()`）。

## M4 第一部分的"生成规则体检"（这一节是最有信息量的）

上面那些规则断言原来都是拿**手工样本**验的（手写一个 spec、铺一块平地）。手工样本能证明
"规则函数写对了"，但证明不了"真实生成出来的那两百个物体满足规则" —— 中间还隔着密度、地表、
规划区、第二遍剔除、冲突修复。所以最后补了一遍**在真实产物上量的独立体检**：

对 8 个模板各生成一次（按模板**自己的**世界档建网格，与真实入口一致），生成完再跑一遍
`ConflictDetector`，要求终态 0 冲突。第一版跑出来是失败的，而且抓出**四个真 bug**：

1. **树顶穿出天花板（39 个越界物体）**。世界档的地形上限贴着天花板（新手档地表能到 15、
   网格高 16），而阔叶树有 7.3 米高 —— 高处的树顶直接伸到世界外面，修复器挪不动就删，
   实测 `high_mountain` 30 棵树被删到只剩 9 棵。修法：**放置时要求头顶有净空**
   （`top + 1 + 树高 ≤ sizeY`），高处自然形成**林线**。
2. **建筑穿出天花板（74 个越界物体）**。同一类问题，发生在建筑上：一块"四角高差合格"的
   高山平台会被圈成地块，然后在 y=16 的地面上盖 3 米墙 → 屋顶出界。修法：规划阶段加
   **净空规则**（`groundY + buildHeight ≤ sizeY`，`buildHeight` 默认 5 米）。
   附带修掉一个**文案 bug**：越界提示只写了 X/Z，于是竖直越界显示成一行 X/Z 完全正常的文字
   （"x -0.3~12.1（界内 ±23.5）"）—— 一条读不出原因的日志比没有日志更费时间。现在会写明是哪个轴。
3. **"允许树冠贴着长"直接把冲突检测喂爆**。第二版间距用的是 `树冠半径 × 2 × 0.95`，
   系数 0.95 < 1 **保证**了相邻树冠的包围盒必然相交 → 每张图几十处"重叠" → 修复器挪不动就删。
   修法：系数改成 1.02（`max(类别下限, 2 × 包围盒半径 × 1.02)`），从源头不产生这类冲突。
   **删除是最后手段，不该变成主路径**（实测：删掉的树从 21 棵降到 0~5 棵）。
4. **参数里的世界档与真正的网格不一致时，地形会算到网格外面**。`generateHeightmap` 按
   "参数里的 maxHeight"算到 21 格，而网格只有 16 格高 → `setVoxel` 静默失败、地形被截到 15，
   但高度图仍然告诉后面所有阶段"地表在 21"。修法：`terrainParamsWithRatios()` **以网格为准**
   夹高度，并且**夹了要在日志里说一声**（不静默改参数）。

**体检还纠正了我自己的一个错误做法**：第一版体检对 8 个模板全用新手档建网格，而其中 7 个
模板自己的世界档是 standard —— 那种组合在应用里永远不会出现，它造出的"越界"是假冲突，
把真 bug 埋在噪声里（我确实先被它误导了一轮）。**体检必须和真实入口用同一套参数，
否则它只是在验证一个不存在的世界。**

最终体检结果（8 个模板，种子 909090）：

| 模板 | 世界档 | 物体 | 地块 | 修复 | 删除 | 终态冲突 | 耗时 |
|---|---|---|---|---|---|---|---|
| plain_village | 新手 | 75 | 4 | 1 | 1 | 0 | 94 ms |
| high_mountain | 标准 | 155 | 2 | 13 | 0 | 0 | 64 ms |
| desert_dunes | 标准 | 54 | 2 | 0 | 0 | 0 | 16 ms |
| archipelago | 标准 | 141 | 4 | 12 | 2 | 0 | 54 ms |
| snow_field | 标准 | 65 | 1 | 0 | 0 | 0 | 18 ms |
| volcanic | 标准 | 48 | 2 | 0 | 0 | 0 | 17 ms |
| deep_forest | 标准 | 275 | 2 | 27 | 5 | 0 | 60 ms |
| city_block | 标准 | 242 | 11 | 3 | 1 | 0 | 36 ms |

**断言间的全局污染也是这轮修的**：四个检查模块各自要装假 `document` / 假 `localStorage`，
合到一个进程里跑就会互相污染（一次是 DOM 桩没卸干净，一次是储存里残留了别的模块塞的
120 个自定义物品），失败信息读起来像是模块自己的 bug。我没有去改断言迁就现状，
而是把 `npm run verify` 改成**每个模块一个独立进程**（`scripts/checks/runAll.mjs`）——
进程退出时内核回收全局环境，谁也没法污染谁。代价是启动几次 Node，换来的确定性很值。

## M4.1：用户反馈的第一轮优化（选东西 + 卡顿）

### 一、物品选择步骤太多、看不到全部

**根因不是分页本身，而是顺序**。`#building-panel` 原来的排列是：

```
搜索 → 分类(13 个 tab) → 二级分类 → 排序/只看收藏 → 最近使用 → 内容包 → 【物品列表】
```

手机上要滚过大半屏才看得到"我到底有哪些东西可选"，而列表本身还是每页 24 个、
翻一次页要"点下一页 → 找 → 再点"。两件事叠起来就是用户说的"步骤太多"。

改法：
1. **列表提到最上面**：搜索 → 最近使用 → 分类 → 数量 → **物品列表**。
2. **筛选与排序 / 内容包收进 `<details>` 折叠块**（偶尔调一次的东西不占主视线）。
3. **「最近使用」提到搜索框下方**：重复放同一个东西只要一次点击；空的时候整行隐藏。
4. **分页 → 连续长列表**：滚到底自动追加 24 个（`IntersectionObserver`，
   `root` 指定为物品网格这个真正的滚动容器；没有观察器时退化成"显示更多"按钮）。
   原来那条"手机滚 387 个卡片会掉帧"的理由没有被牺牲 —— DOM 仍然是**一批一批**建的。
5. 数量提示改成"共 394 个物品｜当前筛选出 N 个，已显示 M 个｜已选中「X」→ 到场景里点地面放置"，
   把"还能看到多少"和"下一步做什么"都写在脸上。

回归断言（14 条）直接钉住**节点顺序**：`item-grid` 必须排在 `catalog-sort` / `catalog-packs`
之前。这条很容易被后人"顺手往上面加一个开关"破坏，而破坏之后没有任何功能会报错 ——
只是又变回"找不到东西"。

### 二、运行卡顿：实测出来的三个每帧开销

用 Node 把纯 CPU 部分单独量出来（没有浏览器也能量这些），三个都是"代码看着正常、
但每帧在做可以不做的事"：

| 问题 | 修前（实测） | 修后（实测） | 做法 |
|---|---|---|---|
| 内容统计热力图挂在每帧路径上 | **1.02 ms/帧**（60 FPS 下每秒 61 ms） | 每 400 ms 一次，均摊 **0.026 ms/帧** | 面板数据统一走 `uiTick` 节流（原来是"先算后节流"：面板内部节流只挡住了 DOM，挡不住计算与分配） |
| 支撑面索引：镜头一动就全量重建 | **1.62 ms/帧**（241 个物体；手机再乘 3~5） | **0.034 ms/帧** | 缓存签名里的焦点坐标量化到 4 米格 + 按 `FOCUS_MARGIN` 放大统计半径；动态物体仍每帧重建（否则"站在滚动的球上"会用到过期顶面） |
| 区块网格重建：预算按**块数**给 | 3 块/帧 ≈ **24~44 ms/帧**（单块 3~5 ms、最慢 18 ms），标准档要 12 帧、大档 48 帧才追平 | 改成**按时间**给预算（4 ms/帧，至少 1 块） | `VOXEL_CONFIG.meshBudgetMs`；块数上限从 3 提到 8 只作为"便宜区块"的护栏 |

另外把性能面板的**阶段拆分**补全了：以前只有"物理 / 模拟 / 渲染"三段，
而"渲染"是**残差**（扣掉前两段的一切）—— 于是区块重建、支撑面、UI 面板全被算进"渲染"，
面板会一本正经地报"渲染是瓶颈"，把人引到错误方向。现在分成
`物理求解 / 水沙模拟 / 区块重建 / 支撑面索引 / 视锥剔除 / UI 面板 / 交互拾取 / 渲染提交`，
并且**各段各自计时**、渲染才是残差。慢帧记录与"最慢阶段"都显示中文标签。

**没有测量的部分**（照实说）：真实帧率、GPU 时间、手机上的实际手感。
容器里没有浏览器，我量的是"主线程上这些活要花多少毫秒"，
它们与帧率的关系是明确的（每一毫秒都从 16.7 ms 的预算里扣），但最终 FPS 得由你在手机上确认。

## M4 第二部分 · 第 6 批（性能优化）的记录与实测

这一批是在**第 3~5 批之前**做的，理由：流体求解器的单帧成本决定了后面耦合与沙土的预算，
而且它是"10000 粒子 60 FPS"这条验收目标的最大缺口。**先量，再改**，下面是量与改的记录。

### 实测结果（10000 粒子，Node 单进程，与浏览器同引擎）

| 阶段 | 优化前 | 优化后 | 说明 |
|---|---|---|---|
| 邻居收集 | 47.3 ms | **44.5 ms** | 内联扫描 + AABB 格剔除 + 哈希去重，但这一项**受内存延迟支配** |
| 密度 | 3.0 ms | 1.6 ms | 复用邻居偏移缓存 |
| 压力 | 50.8 ms | 55.1 → **20.4 ms**（LOD 1 次迭代） | 偏移缓存 + λ 公式修正；2 次迭代时是 55 ms |
| 碰撞 | 23.5 ms | **10.7 ms** | 建筑障碍索引的键从字符串改成整数 |
| 速度/黏性 | 10.5 ms | 10.8 ms | 未改 |
| **合计** | **136 ms** | **84.8 ms**（LOD 1 次迭代） | 桌面 10000 粒子约 12 FPS（Node 单线程） |

**如实交代：没有达到"10000 粒子 60 FPS"（16.7 ms）**，差距约 5 倍。
这不是"再调几个参数"能补上的：邻居收集与压力是**内存延迟主导**（实测 46.8 个候选/粒子、
每次散读约 63 ns），要再快一个量级需要"按空间哈希重排粒子数组"（让邻居在内存里连续），
那是求解器的结构性改动；或者把求解搬进 Worker（主线程成本归零，流体自身降到 ~12 Hz）。

### 这一批抓到的真 bug（比性能更重要）

**λ 的分母少了一项**。PBF 的约束梯度平方和的正确形式是：

```
Σ_k |∇_{p_k} C_i|² = |(1/ρ0)·Σ_j ∇W_ij|²  +  Σ_j |(1/ρ0)·∇W_ij|²
                       ^^^^^^^^^^^^^^^^^      ^^^^^^^^^^^^^^^^^^^^^
                       我第一版只算了这项        这项才是主体（对称排布下第一项几乎完全抵消）
```

后果：分母趋近 0 → λ 被放大几千倍 → Δp 变成"巨大 λ × 几乎抵消的梯度和"的残差 →
每帧上百个粒子被"位置修正上限"兜住 → **水自己炸开**（12 帧从 0.64 米铺到 2.19 米、
平均速度 6 米/秒）。而这个 bug 的症状极其阴险：**密度误差只有 26%，看起来完全正常**。

它是被"偏移缓存"这个优化**暴露**出来的（缓存让第二次迭代用了过期几何，残差对不一致极敏感），
修法是两处：补齐公式，以及**位置变化之后立刻刷新偏移缓存**（见 `refreshOffsets`）。
断言里现在有一条直接盯着"位置修正被上限夹住的粒子数"——那是"水在炸"最灵敏的征兆。

### 结构性优化：静止跳过（活跃区域）

一池静止的水原来每帧仍然要跑完整 PBF。现在整池水平均速度连续 60 帧低于 3.5 cm/s 就**跳过整个求解**，
直到有事件唤醒它（生成/移除粒子、增删冻结区、改类型/重力）。

判据里的 3.5 cm/s 是**量出来的**：PBF 是位置法求解器，水的平均速度不会降到 0，
实测落地后是 2 秒 0.071 / 4 秒 0.031 / 6 秒 0.018 m/s 的残余"呼吸"。
阈值取 0 会让整池水永远进不了静止状态 —— 这条优化就等于没做。

实测效果：静止时单帧 **0.0000 ms**（原来是 100 ms 量级）。
**如实说明它的边界**：这是"整池静止"，不是"逐粒子休眠" ——
大部分静止、少数在动的水池不会被跳过。逐粒子休眠要处理唤醒传播，代价与收益的账还没算清。

### 其它两处优化

- **建筑障碍索引用整数键**：原来每次探针都拼一次 `` `${bx},${bz}` `` 字符串（每帧 6 万次字符串分配），
  改成 `(bx+128)*256+(bz+128)` 之后碰撞相位 23.5 → 10.7 ms。
- **邻居偏移缓存**：把邻居的相对位置缓存下来（7.7 MB），密度与压力不再反复按随机下标读坐标。
  它带来了一次近似（两处注释都写明），也是它暴露了上面那个 λ 的 bug。

### 一次失败优化（记下来免得再犯）

我为了让"邻居格"的内存访问更连续，在 `cellsWithin` 里加了一次 `subarray().sort()` ——
**整体从 47 ms 涨到 138 ms**（每粒子每帧一次排序，20000 粒子就是每帧 20000 次）。
27 次随机访问的代价远小于排序本身。代码里留了注释，别"顺手优化"回来。

## M4 第二部分 · 第 3 批（沙土物理）

### 沙从"一种体素"变成"有状态的格子"

| 属性 | 存储 | 作用 |
|---|---|---|
| 湿度 | `Uint8Array` 0~255 | 决定安息角（干 34° / 湿 45° / 饱和 15°） |
| 稳定性 | `Uint8Array` 0~255 | 沙崩前的征兆；第 5 批的"压塌脆弱结构"也用它 |

内存：大档 192×32×192 → 每个属性 1.18 MB，两个属性 2.4 MB（一次性分配，换图才重建）。

### 安息角：三个锚点 + 实测坡度

`湿度 → 安息角` 用**分段线性**插值，三个锚点精确命中（诚实起见，中间过程没有可信数据，
编一条曲线只会显得"更科学"而不可验证）：

| 状态 | 湿度 | 安息角 | 滑动水平行程 `1/tan(θ)` | 实测堆出来的坡度 |
|---|---|---|---|---|
| 干沙 | 0 | 34° | 1.48 格 | **31.6°** |
| 湿沙 | 0.5 | 45° | 1.00 格 | 45° |
| 饱和沙 | 1 | 15° | 3.73 格 | **11.3°** |

实测值与目标值差 2~4° —— 这是离散格子的固有误差（沙只能"走整数格"），
所以断言钉的是"两者分得开、且落在合理区间"，不是"精确等于 34°"。

### 这一批踩的两个坑（都写进代码注释了）

1. **把"滑动距离"当成了"前瞻要求"**。一次滑动是"水平走 d 格、竖直落 1 格"，
   形成的坡度是 `atan(1/d)`；所以 `d = 1/tan(θ)` 意味着 **d 就是实际走多远**。
   我第一版把它写成了"要求前方 d 格都空、但仍然只走 1 格"—— 那是**反的**：
   要求越多越难滑，坡度反而更陡。症状是干沙与饱和沙堆出来的坡度**一模一样**（33.7°），
   也就是"湿度完全没起作用"。
2. **`canSlideInto` 多要了一条"目标下方必须有支撑"**。斜坡上的斜下方格，它下面本来就是空的
   （斜坡之所以是斜坡就是因为下面没东西），于是这条要求让沙**永远不会沿斜面滑**。
   正确判据只有两条：目标是空气 + 目标上方不是实心块。

另外两处"测试自己写错"的教训也记在断言旁边：用 `new World(...)` 造"平地"其实会生成真实地形
（一口气红了 7 条，其中 5 条是测试的错）；以及一个我自己算错的阈值（0.5−0.02 = 0.48，我却断言 > 0.49）。

### 沙崩与可视化

- **连锁**：一格动 → 唤醒邻居 → 邻居继续滑；一步搬动 **≥12 格**记为一次"沙崩事件"
  （阈值取 12：实测 2×2×6 的沙柱第一步搬动 20 格，那显然是"塌了"；定太高会漏，定太低会刷屏）。
- **可视化**（可在面板开关）：颜色按**稳定性**着色（不是只看湿度 —— 只看湿度的话，
  一堆压得很沉的干沙会被画成"很稳"），每个活跃格画一条"最陡方向"线，
  最近一次沙崩画一个范围框。所有线段合并成一条 `LineSegments`（1 次 draw call）。
- **活跃区域**：只有活跃格会被处理。平铺的沙层搬动数为 0、活跃集为空、单步耗时 < 0.01 ms
  —— 这三条都在断言里钉着。

### 沙土编辑工具（上帝视角笔刷）

堆沙（按 `cos(π/2·d/r)` 衰减堆出沙丘，不是圆锥）/ 挖沙 / 湿沙 / 干沙 / 凝固。
每个工具有独立节流（凝固 300 ms 最长 —— 它不可逆，不该被误触连点）。
凝固会把沙变成石头并**从活跃集里摘掉**（石头不会被沙崩搬走，断言里有）。

## M4 第二部分 · 第 4 批（流体-刚体双向耦合）

### "双向"在这份实现里的确切含义（先说实话）

- **流体 → 刚体**：浮力（排开体积）、阻力（相对速度）、推动（水流速度）、
  冲击（迎面动压）、力矩（浮心偏移的扶正力矩 + 角速度阻力）。**这一批的主体。**
- **刚体 → 流体**：流体求解器把刚体当**静止边界**（`FluidBoundary.isSolid` 把建筑包围盒算成固体），
  所以水会绕开箱子、会被箱子挡住。但**运动中的刚体不会带动水**（没有尾流）——
  那需要把刚体速度作为 PBF 的边界条件传进去。**没做**，如实记在这里。

### 公式与它们能被精确验证的部分

| 项 | 公式 | 断言怎么验的 |
|---|---|---|
| 浮力 | `ρ流体 · V排开 · g · 浮力系数` | 1 m³ 立方体全浸在水中 → **精确等于 9810 N**（相对误差 < 1e-6）；半浸 → 4905 N |
| 阻力 | `0.5·ρ·Cd·A·|v_rel|·v_rel + λ·v_rel` | 方向与相对速度反号；速度翻倍 → 力约 4 倍（实测比值 3.5~4.5） |
| 推动 | 同上，但相对速度来自水流 | 水在流、物体静止 → 力顺水流方向，且水流越大推力越大 |
| 冲击 | `ρ·A·(v_rel·n)²·换算系数` | 动压精确等于 `ρv²/2`（3 m/s → 4500 Pa）；速度翻倍 → 动压 4 倍 |
| 扶正力矩 | `r × F浮`，r = 浮心 − 重心 | 只在 +X 侧浸没 → 浮心 x > 0、力矩绕 Z 为**负**（把物体扳回来） |
| 角速度阻力 | `-ω · k` | 自转物体受到反向力矩，转速越高力矩越大 |

阻力为什么额外加**线性项**：纯二次阻力在速度趋近 0 时力也趋近 0，
数值上物体"永远停不下来地微动"。这是游戏物理的通行做法，**不是**真实流体模型
（真实低速区是 Stokes 阻力，系数与形状强相关）。

### 每帧 2~3 次迭代的做法

不是"把求解器跑 3 遍"，而是**把力分 3 次施加**，每次用更新后的速度重算相对速度 ——
这样"物体已经动了、阻力应该变小"在同一帧内就收敛，抑制"物体在水里来回抖"。
迭代次数在预设里可调（真实 3 / 游戏 2 / 夸张 2），断言里钉着这三个数。

### 三套预设

| 预设 | 浮力 | 阻力 Cd | 冲击 | 迭代 | 用途 |
|---|---|---|---|---|---|
| 真实 | 1.0 | 1.1 | 1.0 | 3 | 木头浮、石头沉、水里推东西费劲 |
| 游戏 | 1.0 | **0.55** | 1.6 | 2 | 玩家还能开船、还能推动箱子 |
| 夸张 | **1.35** | 0.35 | **4** | 2 | 洪水冲垮房子、海啸镜头 |

数字是**视觉调参**的结果，不是物理常数。

### 安全阀（这是耦合最容易炸的地方）

粒子速度可以到几十米/秒，密度采样又是离散的 —— 一次采样误差就能产生几十万牛顿的力
把物体射到天上。所以每个物体每帧的合力/力矩都有上限，**夹住的次数被如实统计**
（面板与 `describe()` 里都会显示"⚠ N 个被力上限夹住"）。夹得多了说明参数不合理，
而不是"物理就是这样"。

### 这一批抓到的 bug

构造函数忘了记录预设名：`presetName` 的字段初值是 `'game'`，而构造函数只设了 `config` ——
于是 `new FluidRigidCoupling('realistic')` 的 `describe()` 永远显示"游戏"。
断言红在一个看起来完全不相关的字段上（"预设：describe() 给出中文摘要"），
定位到之后发现是"两个字段一个设了一个没设"。

另外给 `UniformFluidField` 的流速参数加了缺字段补 0 的防御：NaN 会**静默传播**到力里
（Rapier 收到 NaN 力时物体直接消失），那种 bug 极难查，补 0 比让它传下去便宜得多。

## M4 第二部分 · 第 5 批（沙水交互 + 沙掩埋压塌）

### 四件事

| 现象 | 触发条件 | 实现 |
|---|---|---|
| **变湿** | 流体盖住沙（fullness > 0.25） | 调用 `SandSystem.moistureFromFluid`，吸水速率 ∝ 流体占比 × dt |
| **侵蚀（泥流）** | 流速 > 1.6 m/s **且**沙的湿度 > 0.55 | 概率化（`erodeRate × dt`）：沙格变空气 + 往流体里加粒子 |
| **沉积** | 流速 < 0.35 m/s **且**水里还有粒子 **且**下方是固体 | 移除几个粒子 + 放一格**饱和**沙 |
| **压塌** | 建筑顶上的沙格数 > 阈值（默认 18） | 把建筑转成**动态刚体**（走 M3 已有的 `physics.setMode` 路径） |

侵蚀为什么是概率化而不是确定性阈值：确定性的"到速度就冲走"会让河床在一瞬间被削平，
看起来像 bug；概率化之后表现是"水慢慢把岸边啃掉"。

### 三处如实说明的取舍

1. **体素 ↔ 粒子的换算不守恒**。1 m³ 体素按静止间距应该是 244 个粒子，
   但那样"冲掉一格"就瞬间多出 244 个粒子，几百格就把粒子上限吃满。
   这里用**观感换算**（1 格 → 6 个粒子）。代价：浑水看起来比实际偏淡。
   收益：能稳定地跑，而不是一冲就崩。
2. **dt 被夹在 0.1 秒**：卡帧之后一帧把整片沙浇透会很难看，也会让侵蚀瞬间发生。
   夹住之后最多按 0.1 秒算（断言里钉了这一条）。
3. **压塌是启发式**：只看建筑顶上的沙格数，不区分承重结构、不算力矩。
   它保证"沙压得够多就会塌"，不保证"塌在正确的格子上"。

### 这一批的测试教训

- **"饱和沙会摊开"不是泥流**。我第一版拿"一层 1 格厚的平沙"测泥流 ——
  那种场景**没有落差**，沙无处可流，断言天生会红。正确的泥流断言是三步闭环：
  **冲刷 → 搬运 → 淤积**（现在就是这么写的：上游冲走 N 格、水里多出粒子、下游淤积出新沙）。
- **`stats` 是单次调用的统计**（这是对的设计：面板每帧读"这一帧做了多少"）。
  我第一版在循环结束后读 `stats.deposited` 去验证"累计沉积了多少"，那永远是 0 ——
  要验证累计就必须自己累加。

## M4 第二部分 · 第 8 批（流体存档 + 六个教学关卡）

### 流体存档：量化 + 打包

直接把 `Float32Array` 塞进 JSON 会膨胀 3~5 倍（20000 粒子 ≈ 480 KB 原始 → 两三兆文本），
而 localStorage 配额只有 5 MB 左右 —— 存一次水就爆。所以做两件事：

| 量 | 精度 | 理由 |
|---|---|---|
| 位置 | **1/512 米（约 2 毫米）** | 粒子半径 80 毫米，2 毫米误差看不出来 |
| 速度 | **1/64 米/秒** | 0.016 m/s 的误差在视觉上无意义 |
| 沙的湿度 | **1/255** | 它本身就是 0~1 的百分比 |

位置存的是**相对包围盒的偏移**再量化（一桶水只有几米、一条河跨几十米，
固定绝对精度会在小范围浪费位数、在大范围精度不够）。

**实测压缩率 50%**（24 字节/粒子 → 12 字节/粒子）。这里要说清一件事：
RLE 在这份数据上**基本帮不上忙**（量化后的粒子数据是高熵的），
收益**全部来自量化**。所以 `measure()` 里的"原始大小"按**未量化的 float32**（24 字节/粒子）算 ——
我第一版写成 12，于是压缩率永远显示 100%，等于把量化的收益藏起来了。

断言分三层：粒子数**精确相等**（少一个是 bug，不是精度问题）、位置/速度误差在量子内、
损坏/版本不符/魔数不对的载荷必须报**中文错误**而不是静默返回空。

### 六个教学关卡

水流向低处 / 浮力与船 / 水压与闸门 / 沙崩 / 泥流 / 洪水，
每关一个纯函数判定 `(snapshot, elapsedMs) => boolean`。
判定阈值刻意取得很宽（"铺开 3 米"而不是"精确达到 15° 安息角"）——
这些关卡是**引导玩家发现功能**，不是考试；让玩家为了通关去精确操作一个离散近似模拟是错的。

断言里最重要的两条是**反面**：
- **什么都不做不会通关**（空快照喂进去，六关全部不过）；
- **该卡住的地方要卡住**：物体正在下沉时"浮力"关不通关、只有侵蚀没有淤积时"泥流"关不通关、
  只造了冻结区但里面没水时"闸门"关不通关。

### 这一批抓到的两个真 bug

1. **`decode()` 在"粒子数为 0"时提前返回**，于是**沙的湿度根本不会被读回来** ——
   而"只弄湿了沙、没有水"是完全合法的一种存档。症状：写进去 0.75、读回来 0。
2. **`unpackBytes(packed, -1)` 会把最后一个字节砍掉**（`subarray(0, -1)` 的语义）——
   我原本用它表示"不知道长度"。改成把长度写进载荷（顺带让格式自描述）。

## M4 第二部分 · 第 7 批（压力测试 + 负载热力图 + 帧录制）

### 10 个场景与它们**真实的**上限（这一节最重要）

场景表是纯数据（`StressTestScenes.ts`），执行在 Engine 的 `applyStressPlan`。
但"场景名字"与"实际能跑出多少"之间有几处**必须说清的落差**，全部写进场景的
`blindSpots` 与报告里：

| 落差 | 实际情况 |
|---|---|
| **1000 箱子堆叠** | 桌面动态刚体上限 **800**（`performanceLimits().dynamicMax`），所以永远跑不到 1000，摘要里显示"请求 1000 → 800" |
| **100 门同开 / 50 吊桥同放** | 门与桥是**动态刚体**，**没有铰链关节** —— 真正的"门绕合页转""吊桥放下"在 M3 的 `drawbridge_50` 场景里（带关节）。这两个场景压的是求解器与碰撞检测，不是关节求解。摘要里明写这一句 |
| **洪水冲建筑** | 20000 粒子上限 = **81.9 m³ 水**；把 20×20 街区淹到 0.5 米要 ≈48828 个粒子（上限的 2.45 倍）。所以只能做"街道浅水"（0.33 米深），**冲不倒建筑** |
| **大型城市** | 现成地图生成给不出"大型城市"：建筑数 = `round(6 × 建筑密度)`，「城市街区」1.8 → **11 栋**。这个场景名不副实，写在 `blindSpots` 里 |
| **船在水中** | 4000 粒子摊在 5×5 池上只有 **0.66 米深**（够 `boat_row` 小艇，不够大船） |
| **5000 粒子瀑布** | `emitBox` 只生成一次、不持续补水，落完就堆住了 |
| **大型沙崩** | 世界档固定 `standard`（96×96），200 列沙要占 75×21 米，勉强放得下 |

### 目标帧率的出处

需求给的通过标准只有两个数：**桌面 30 FPS+、移动端 15 FPS+**。
场景表里的 `targetFps` 就是这两个数（注释里标明了来源）。
"采样 0 帧一律判不通过"—— 没测不等于通过。

### 对比与人为阈值

`compareRuns` 判定"变快/变慢/基本一样"的带宽是 **3%**，
**这是我人为定的，需求里没有**：同一场景同一机器连跑两次差 1~2% 是常态（GC、降频），
阈值取太小会把噪声报告成"变快了"。取 3% 是"明显超出噪声"的最小量级。

同理 `LOW_END_EXTRA_SCALE = 0.6`（低端机再降一档）也是人为定的 —— 需求只说"再降一档"没说降多少。

### 负载热力图：**不是**每帧实际耗时（说三遍）

WebGL 没有"按屏幕区域计时"的接口；`EXT_disjoint_timer_query` 只按 draw call 计时，
而区块合批之后连"哪个 draw 属于哪一格"都没有。所以图上数字**永远是加权物件数**：

- 权重：流体/沙土/地形/其它 = 1（单位口径，**不代表**真实开销相等），刚体 = 4（**估计值**）；
- UI 上三处明写：canvas 左下角的角标（**画进位图**，截图传播也带着）、色标的副标题
  「估计值，不是毫秒」、`describeHeatmap()` 末尾的限定句；
- 不含相机朝向与视锥剔除 —— 视野外的物件实际开销更小，本图不计这一点；
- 世界尺寸或原点没给时**不分箱**（`cells` 长度为 0），而不是画一张 8×8 的全 0 假图。

### 帧录制

环形缓冲 3600 帧（60 秒），满了覆盖最旧的并**如实报告丢了多少帧**。
没在录制时 `sample()` 的开销约等于空函数（实测：10000 次调用的耗时与调空函数相同）。
`durationMs` 取帧时间戳的首尾差，**不是** `stop() - start()`（两者时钟基准可能不同）。

### 顺带修掉的两个 DOM 重名 bug（子代理在写断言时查出来的）

1. 我新加的压力测试面板用了 `id="stress-panel"`，而 **M3 的「🌡 应力」面板已经占用了它** ——
   `StressPanel.ts` 用 `must('#stress-panel')` 找的是第一个，于是"应力开关"会作用到压力测试面板上。
2. 沙面板的 `#sand-angle` 与地形笔刷里那个同名滑杆冲突（`SandPanel` 的说明文字会写到滑杆上）。
   已改成 `#sand-repose-note`。

## M4 第二部分 · 第 6 批收尾（流体求解 Worker）

### 已交付的能力

`src/workers/fluidWorkerTypes.ts` + `fluidWorkerCore.ts` + `fluidWorker.ts` + `src/world/FluidWorkerRunner.ts`，
72 条断言（`scripts/checks/fluidworker.check.ts`）。照 `ConflictRunner` 的模式写的：

- Node 里（没有 `Worker` 全局）**每一条**结果都是 `source: 'main-thread'` + 中文回退原因 ——
  回退是这一轮的默认路径，不是偶发分支；
- `source` 与 `fallbackReason` **不允许自相矛盾**（回退必须说明原因，走 worker 必须没有原因）；
- 打包/回传耗时的**真实数字**被记下来（没走 worker 时为 `null`，不谎报成 0）；
- 边界快照打包→解包之后，对同一批采样点的 `isSolid` 回答与原边界**完全一致** ——
  这是"搬移没有偷偷缩小能力"的直接证据。

### 接线状态（并更正上一版 README 里的一处**错误结论**）

上一版 README 里我写了"worker 结果没有回写进粒子池" —— **那是错的**。
我当时用 `grep "pool\." FluidWorkerRunner.ts` 没找到写回，就下了结论；
实际上写回在 **`src/workers/fluidWorkerCore.ts` 的 `applyPoolDelta()`** 里，
而且带三重一致性校验（容量 / `highWater` / 活跃粒子数不一致就**拒绝写回**）——
那三条校验很关键：等待回包期间如果玩家倒水或抽水，池子已经变了，
不加校验直接写回会让粒子**整体错位**（比"没写回"糟得多）。

现已在 `Engine.updateFluid()` 里接线：
- 有 Worker 时走 Worker，没有时 runner 内部同步回退，**判定逻辑只有一份**；
- runner 忙（上一帧还没回来）时这一帧不再同步算一遍（那等于把算力翻倍用在同一段时间上）；
- 走 worker 时同一帧里 `applyFluidCoupling` 读到的是**上一次完成的求解结果**。
  视觉上看不出（水位是连续的），但含义要写清：**流体自身的更新率 = min(帧率, worker 完成率)**；
- 面板可读 `fluidSolvePath`：`worker N 帧 / 主线程回退 M 帧`，不是含糊的"已启用"。

**仍然没做的**：浏览器里实测。容器里没有 `Worker`，Node 的 `worker_threads` 不是浏览器 Worker，
所以 worker 真身（`new Worker(...)` 起来、跑、回包）**只做了构建层面的验证**，
没有在浏览器里跑过。这一条只能由人来验收。

### 构建层面的证据（worker 真的被打包了）

`npm run build` 的产物里**两个 worker 都单独成块**，而且我在预览服务器上实测过 HTTP 200：

```
dist/assets/fluidWorker-BIO3d-dp.js     27.74 kB    → 200 / 27743 字节
dist/assets/conflictWorker-C_GVwfmu.js              → 200
```

这证明三件事：① worker 入口被 Vite 识别并单独打包（不是被内联进主 bundle）；
② URL 被按 `base` 重写成 `/god-sandbox/assets/...`（子路径部署不会 404）；
③ `new Worker(new URL(...))` 的写法是静态可分析的。

**没证明的**：worker 真身跑起来（容器里没有 `Worker`，Node 的 `worker_threads` 不是浏览器 Worker）。
那一层只能靠人在浏览器里点一下。
